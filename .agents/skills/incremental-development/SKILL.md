# 小さな単位での開発

- できるだけ失敗するテストから始め、最小の実装で通してから整える。テストを書く価値が低い変更では、適切な確認方法を選ぶ。
- 一度に大きく作らず、動作を確かめられる小さな単位で部品を追加・変更する。
- 同じ処理が 2 か所以上に現れたら、共通化すると読みやすくなるか検討する。違いが大きい処理まで無理にまとめない。
- ファイルが長くなって見通しが悪い場合は、責務の境界で分割する。React では状態管理や副作用をカスタム Hook、表示をコンポーネントに切り出すことを検討する。行数だけを理由に細分化しない。
- 機能追加や修正に伴ってファイルの責務が変わったら、ディレクトリ構成も見直す。既存の配置に固執せず、画面の入口と関連する処理を探しやすい場所に置く。たとえば `apps/web/src/features/travel` では Page を `pages/` に集め、Page 以外は機能の直下に置く。Page のない機能に空の `pages/` は作らない。
- 動作を確認できる小さな変更単位でコミットを積む。機能変更と構成整理を分けられる場合は、別々のコミットにする。

## PR の粒度

- 1 PR は一つのレビュー可能な振る舞い・変更単位にする。関連 Issue 全体を一つにまとめず、依存関係に沿って DB・モデル → API → 画面のように分ける。
- 手書きの実装とテストを合わせて、差分は **200〜400 行程度、変更ファイルは 10 件程度まで**を推奨する。生成物・ロックファイルは行数の目安から除く。
- 500 行を超える見込みなら、着手前に分割単位と PR 間の依存関係を決める。分割すると動作やレビューが成立しない場合は、その理由を PR 本文に書く。
